### 踩坑：grep 在 bash 里被引号吃掉

`grep -o "renderKnowledge[A-Za-z]*|openKb[A-Za-z]*" index.html` 返回**空**，一度以为知识库前端没做。
真因：管道符 `|` 落进 Windows 下 `findstr` 风格解析，命令实际跑成了两个 pattern 不带 `|` 的 grep。
→ **教训：在这台机的 Git Bash 里，`grep -o "a|b"` 的 alternation 不可靠，改用多个 `grep -n <单个词>` 或走 Grep 工具。**
差点把「已实现」误判成「未实现」去做重复劳动。

## 追查「AUTO-STOCK 一直卡在 0/95728」+ 手动同步异常

### 用户反馈

1. 截图：下载浮窗卡在 `正在传输文件 (0 / 95728)` 不动
2. 「我手动同步过了哟刚才」

### 结论一：卡住不是 bug，是在传 3.1 GB

实测 AUTO-STOCK 在阿里云 `/home/<ssh_user>/AUTO-STOCK`：

| 口径 | 文件数 | 数据量 | 扫描耗时 |
|---|---|---|---|
| `all=true`（用户点的「全部」） | **95,728** | **3,191.6 MB** | find 3.26s |
| 默认过滤 | **2,329** | **212.7 MB** | find 0.86s |

- 本地 `D:/local/AUTO-STOCK` 是**空的**（0 文件）→ 全部要传，没有增量跳过的可能。
- 构成：`node_modules`(89个目录) 35,977 · `venv` 8,282 · `.git` 6,474 · `__pycache__`(393个) 3,731 · `dist`(249个) 3,517。
- 扫描本身很快（3.26s），卡的是传输 3.1GB。**建议不勾「全部」重跑**。
- 顺带发现过滤清单漏了 `.next`/`dist`/`build`/`target`/`coverage` 等构建目录，未改（`dist` 名字太通用有误伤风险）。

### 结论二：手动同步暴露了 429 限流 bug（真 bug，已修）

`latest.json`（23:23:40）显示：`{api_failed: 2, skipped_breaker: 13}`，**耗时 73.5s**。
同步本身是成功的（15/15、failed=0），但 LLM 全军覆没。

**排查链**（关键是不能靠猜）：
1. 发现 `api_failed` 的项目**没有 `llm_error` 字段** → 定位到 `sync_all` 的 `project_entry`
   漏了 `llm_error`（`sync_single` 那份一直有，两处长期不一致）→ 已补。
2. 直接用真实配置复现 `apply_llm_analysis('AUTO-STOCK', ...)`，拿到真实错误：
   **`HTTP 429 {"error":{"message":"inference exceeds tpm/rpm limit"}}`**
3. 对照实验：小 prompt（899 字符）**成功**，26.4s 返回完整 JSON；大项目（46,162 字符 / 29k token）**429**。
   → 证明是 TPM 上限，不是网络卡死、不是超时、不是 key 失效。

**这是 v1.4.24 熔断的误伤**：熔断把任何 `api_failed` 当「provider 挂了」，
一次限流导致一轮里 **13 个健康项目全被跳过**（它们本来能成功的，只是排队时被熔断了）。

### 修复（三处，均已回归锁定）

1. `llm_analyzer._call_openai`：遇 429 退避重试，读服务端 `Retry-After`；
   新增 `LLM_RATE_LIMIT_RETRIES=3` / `LLM_RATE_LIMIT_BACKOFF=20`（环境变量可调）。
   顺带补了缺失的 `import time`。
2. `sync._update_llm_breaker`：增加第 4 参 `error`，含 `429`+`limit` 时**不计入熔断**。
3. `sync.sync_all`：项目间节流 `LLM_PROJECT_SPACING=8` 秒；
   只对真发过请求的（`analyzed`/`api_failed`）等待，`reused` 不等。
