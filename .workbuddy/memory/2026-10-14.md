## 追查「AUTO-STOCK 一直卡在 0/95728」+ 手动同步异常

### 用户反馈

1. 截图：下载浮窗卡在 `正在传输文件 (0 / 95728)` 不动
2. 「我手动同步过了哟刚才」

### 结论一：卡住不是 bug，是在传 3.1 GB

实测 AUTO-STOCK 在阿里云 `/home/<ssh_user>/AUTO-STOCK`：

| 口径 | 文件数 | 数据量 | 扫描耗时 |
|---|---|---|---|
| `all=true`（用户点的「全部」） | **95,728** | **3,191.6 MB** | find 3.26s |
| 默认过滤 | **2,329** | **212.7 MB** | find 0.86s |

- 本地 `D:/local/AUTO-STOCK` 是**空的**（0 文件）→ 全部要传，没有增量跳过的可能。
- 构成：`node_modules`(89个目录) 35,977 · `venv` 8,282 · `.git` 6,474 · `__pycache__`(393个) 3,731 · `dist`(249个) 3,517。
- 扫描本身很快（3.26s），卡的是传输 3.1GB。**建议不勾「全部」重跑**。
- 顺带发现过滤清单漏了 `.next`/`dist`/`build`/`target`/`coverage` 等构建目录，未改（`dist` 名字太通用有误伤风险）。

### 结论二：手动同步暴露了 429 限流 bug（真 bug，已修）

`latest.json`（23:23:40）显示：`{api_failed: 2, skipped_breaker: 13}`，**耗时 73.5s**。
同步本身是成功的（15/15、failed=0），但 LLM 全军覆没。

**排查链**（关键是不能靠猜）：
1. 发现 `api_failed` 的项目**没有 `llm_error` 字段** → 定位到 `sync_all` 的 `project_entry`
   漏了 `llm_error`（`sync_single` 那份一直有，两处长期不一致）→ 已补。
2. 直接用真实配置复现 `apply_llm_analysis('AUTO-STOCK', ...)`，拿到真实错误：
   **`HTTP 429 {"error":{"message":"inference exceeds tpm/rpm limit"}}`**
3. 对照实验：小 prompt（899 字符）**成功**，26.4s 返回完整 JSON；大项目（46,162 字符 / 29k token）**429**。
   → 证明是 TPM 上限，不是网络卡死、不是超时、不是 key 失效。

**这是 v1.4.24 熔断的误伤**：熔断把任何 `api_failed` 当「provider 挂了」，
一次限流导致一轮里 **13 个健康项目全被跳过**（它们本来能成功的，只是排队时被熔断了）。

### 修复（三处，均已回归锁定）

1. `llm_analyzer._call_openai`：遇 429 退避重试，读服务端 `Retry-After`；
   新增 `LLM_RATE_LIMIT_RETRIES=3` / `LLM_RATE_LIMIT_BACKOFF=20`（环境变量可调）。
   顺带补了缺失的 `import time`。
2. `sync._update_llm_breaker`：增加第 4 参 `error`，含 `429`+`limit` 时**不计入熔断**。
3. `sync.sync_all`：项目间节流 `LLM_PROJECT_SPACING=8` 秒；
   只对真发过请求的（`analyzed`/`api_failed`）等待，`reused` 不等。

### 验证

- `run_checks.py` **13/13**

## v1.4.25：下载分批 + 实时速率进度（用户反馈「感觉像卡死」「成功信息也要有输出」）

### 用户原话

> 「关掉了，但是我需要做一次全量，能不能不用一次传那么多，分批，感觉像卡死一样现在。
> 而且下面的成功信息也要有输出才好啊。」

### 根因

前端**本来就有** `case 'batch'` 分支（显示 `已传/总量 + 速率` + 进度条），
但后端**从来不发 `phase='batch'` 事件** —— 只有 `phase='file'`（纯文件计数）。
所以界面只能显示 `正在传输文件 (0 / 95728)`，干等着 → 看着像卡死。

而且旧实现把 9 万多个文件一次塞给**单个 tar**：
① SSH 通道要连续跑几十分钟；② 一批挂掉全盘皆输，前面下好的几千个文件随进程废掉。

### 改动

**后端 `backend/sync.py`**
- 新增常量 `DL_BATCH_SIZE=600`（`DEV_CENTER_DL_BATCH`，≤0 退回旧行为）、
  `DL_BATCH_GAP=0.5`（`DEV_CENTER_DL_BATCH_GAP`）。
- `sync_download` 改成**分批 tar**：每批一个独立 `exec_command`，批间停顿。
- 每批独立 try/except：某批网络中断/解包失败只记 `batch_ok=False`，**不连坐后面的批次**。
- 新增进度事件：
  - `phase='batch'`（传输中，带 bytes/total_bytes/batch/batches/current）→ 驱动前端速率显示
  - `phase='batch_done'`（每批结束，带 batch_ok/downloaded/skipped/failed/bytes）→ 驱动成功信息输出
  - `phase='transferring'` 增加 `batches` 字段
- ⚠️ 取消逻辑改了：分批循环里不再 `raise _DownloadCancelled`（会穿出 finally），
  改为 `cancelled` 标志 + `break`，循环外统一上报 `phase='cancelled'`。
  `_DownloadCancelled` 类**只有 `sync_upload` 还在用**，别拿它去改 download 路径。

**前端 `index.html`**
- `transferring` 分支：显示批次数 + 总字节数。
- `batch` 分支：改为「已传/总量 + 第 N/M 批 + 文件计数 + 速率 + 用时」。
- 新增 `batch_done` 分支：往日志区 `addLog('✓ 第N/M批完成 · 已下载x/y个 · zzzMB')`，
  并刷新下方统计（已下载 / 跳过 / 失败）。
- `file` 分支：带 `bytes` 的事件不再逐文件刷日志（由 batch 汇总），避免日志爆炸。
- 新增 i18n：`sync_batches_unit` / `sync_batch_n` / `sync_batch_ok` / `sync_batch_fail` / `sync_files_done`。

### 真机验证（阿里云_成都 / 小龙虾稿件管理系统）

`DL_BATCH_SIZE=15`（故意调小以验证分批），772 文件 / 307.4MB：

| 指标 | 结果 |
|---|---|
| 批数 | 52 批 |
| 总耗时 | 91.4s |
| 平均速率 | **3,495 KB/s** |
| 结果 | 下载 772 / 失败 0 |
| 事件序列 | `connecting:1 scanning:1 transferring:1 batch:213 file:213 batch_done:52 done:1` |

验证中发现并修掉一个自己的 bug：`transferring` 报的批数用
`len(range(0, len-1, SIZE))+1` 算，772/15 得出 **53**（实际 52）。
改用标准上取整 `(len + SIZE - 1) // SIZE`。
