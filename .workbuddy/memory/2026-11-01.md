### 二、发现的三个真缺陷（全部已修）

**1. ⚠️ LLM 失败会把 AI 分析数据清空（最严重）**

`apply_llm_analysis` 失败时走 `api_failed` 分支，直接把
`llm_features` / `llm_summary` / `llm_tech_stack` 置空 → 写进 `latest.json`
→ **首页的 AI 分析整块消失**。

触发条件极常见：**远端 md 一改（指纹变了）+ provider 超时/限流 → 必现**。
当时侥幸躲过，只是因为指纹恰好没变走了「复用」路径。

**修法**：失败时沿用上次分析结果，status 标 `stale`（数据过期但可用），
同时保留 `llm_error` 让用户知道"这次没更新成功"。
**只有首次分析就失败（真没历史）才标 `api_failed`**。
前端加了 `stale` 状态映射 + `pd_llm_stale` 文案。

**2. 超时没有退避重试**

429 有退避（3 次 × 20 秒），**超时没有** → 直接判失败。
加了 `LLM_TIMEOUT_RETRIES`（默认 2）+ `LLM_TIMEOUT_BACKOFF`（默认 20 秒），
只在 `call_llm_api` 的分发处包一层 `_call_with_timeout_retry(fn)`，
**只对超时重试**（429 走自己那套，鉴权失败/格式错误重试无意义）。

**3. 错误消息在骗人**

`请求超时 (30s)` 里的 **30 是硬编码文案**，实际超时是 `LLM_HTTP_TIMEOUT = 120` 秒。
（第一次读日志时就被它误导了，以为超时只有 30 秒。）4 处全部改成动态取值。

**另外**：大 prompt 自适应放宽硬超时 —— prompt ≥ 12000 字符时，硬超时从 180s 提到 300s
（推理型模型在大输入上本来就慢；AUTO-STOCK 16k 字符实测 120s 不够）。

### 三、新功能 1：首页跑分徽章

首页「服务器状态」面板（环形 / 进度条两种模式）每台机器名称旁显示
**最近一次跑分总分**，颜色按评级（`benchColorFor`）：≥85 绿 / ≥70 强调色 / ≥55 琥珀 / <55 红。
没跑过的显示灰色「—」。

- 数据来自 `/api/bench/compare`（一次拿全部机器）
- **不跟监控的秒级轮询**，只在进首页时拉一次
- 更新时只替换徽章元素，**不整页重绘**（重绘会打断用户输入/滚动）

### 四、新功能 2：跑分历史趋势图（判断超售的硬证据）

**单次跑分只是一个数据点；同一台机器多次跑分的「波动幅度」才是超售的硬证据。**

- 跑分弹窗里加折线图（canvas）+ 最高/最低/平均/**波动**四项摘要
- 波动 ≥20 分 → 「⚠️ 波动很大 —— 高度疑似宿主机超售」；≥10 → 「波动偏大」；<10 → 「表现稳定」
- 数据点颜色按分数评级
- **打开弹窗就能看，不用先跑分** → 历史容器 `#bench-hist` 从「跑分结果区」移到了「弹窗固定结构」
  （⚠️ 移的时候必须确保 `id="bench-hist"` 全页只有一处，否则 `getElementById` 拿到第一个）
- 后端 `/api/bench/{id}/history` **本来就有**，只改前端

实测（阿里云成都 11 次历史）：最高 68.2 / 最低 56.9 / 平均 64.3 / **波动 11.3** →
自动提示「波动偏大 —— 可能存在轻度超售或邻居干扰」。

### 六、踩到的坑

1. **`DATA_DIR` 开发态 vs 打包态不同**：
   开发态 = `项目/backend/data`（**空的**），打包态 = `%APPDATA%/Personal AI Dev Center/data`（真实数据）。
   → 测试脚本不设 `DEV_CENTER_DATA_DIR` 会读到空目录，误判「历史 API 返回 0 条」。
2. **波动值没格式化** → 显示 `11.300000000000004`（浮点误差）。用 `gap.toFixed(1)`。
3. **`test_bench_browser` 偶发 FAIL**：Chrome 在 `setTimeout` 回调前就 dump 了（时序抖动）。
   在 `render()` 后补一个 `step('RENDERED')` 后反而更稳定。
4. **swagger 页面「跑分评估」** 也有对比表，但趋势图只加在单机弹窗里（对比表横着放不适合画时间轴）。
