### 定位过程（已排除是自己新增的 content_mtime 探测）

新工具 `tools/probe_sync_timing.py <项目名>`（**只读**：只跑 find/cat/stat，不改数据、不下载）。
对「打字游戏」实测：

```
[1] SSH connect        :  0.4s
[2] find *.md          :  0.7s  (1 个)
[3] cat README.md      :  0.1s
[4] stat 目录 mtime     :  0.1s
[5] content_mtime find :  0.1s  -> 1784211806.8
----------------------------------------
SSH 侧合计            :  1.4s
```

⇒ **4669 秒全部在 LLM 调用**，v1.4.23 新增的 `content_mtime` find 只花 0.1s（正常，无回归）。
且两项目的 `content_updated_at` 都返回了合理日期（2026-07-16 / 2026-07-05），功能正常。

### 根因

`backend/llm_analyzer.py`：

```python
LLM_HTTP_TIMEOUT = int(os.environ.get("DEV_CENTER_LLM_TIMEOUT", "120"))
response = requests.post(url, headers=headers, json=payload, timeout=LLM_HTTP_TIMEOUT)
```

- `analyze_project()` 每次只调**一次** `call_llm_api`，**无重试循环**，所以不是重试叠加。
- ⇒ **`requests` 的 timeout 没能拦住**：该参数只覆盖 connect/read 两段的「间隔」，
  对 DNS 解析、TLS 握手后的慢速响应等阶段不可靠；本机又是 **v2rayN TUN 全局代理**，
  `token.sensenova.cn` 也走代理，代理侧慢/半开连接会让单次请求挂成几十分钟。
- LLM 配置：provider=商汤科技、model=`sensenova-6.8-flash-lite`、base_url=`https://token.sensenova.cn/v1`。

### 修复方向（**未动手**，等用户定）

1. **硬超时**：用 `ThreadPoolExecutor` + `future.result(timeout=N)` 包住 LLM 调用。
   线程杀不掉，但主流程能按时往下走（不能再用裸 `requests(timeout=)` 当保险）。
2. **增量跳过（收益最大）**：记住每项目参与分析的 md 文件 mtime，全都没变就复用上次 LLM 结果、
   完全不发请求 ⇒ 正常同步可从 114 分钟压到几分钟（SSH 侧本来就只有秒级）。
3. **熔断**：一次同步内某 provider 连续失败 N 次后，跳过后续项目的 LLM 请求。

### 预警逻辑（`computeAlerts()`，index.html:1476，单行函数）

```js
state.projects.filter(p=>p.status==='active'||p.status==='dev').forEach(p=>{
  const dy=Math.floor((Date.now()-new Date(p.lastUpdate).getTime())/864e5);
  if(dy>=7) a.push({level:dy>=30?'high':'medium', icon:'alert-triangle',
                    name:p.name, sub:`内容 ${dy} ${t('alert_days_no_update_tpl')}`})})
```

- **只对 `status ∈ {active, dev}` 的项目**报警，阈值 **≥7 天**（≥30 天升 high）。
- ⇒ 长期不维护、但仍标 `active` 的项目会**永久刷屏**。系统本就有 `status` 字段
  （active/dev/planned/paused），改成 `paused` 即可静音 —— 属「用户没改状态」而非 bug，
  但值得做一个更顺手的入口（一键暂停/归档）。
- `lastUpdate` 的数据源已在 v1.4.23 换成 `content_updated_at || progress.last_update`。
