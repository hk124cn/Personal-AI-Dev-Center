# 2026-11-01（续）

## 加 CPU 抢占率（steal）—— 超售的直接证据

### 关键发现：这个功能**早就存在**，但没人看得见

用户问「轻度超售的提示线还有这种功能吗」→ 查下去发现：

| 层 | 状态 |
|---|---|
| `bench.py` 采集 `cpu_steal_pct` | ✅ **早就有**（`/proc/stat` 第 9 字段） |
| `bench_score.py` 锚点 + 稳定性维度 | ✅ **早就有**（`(0.2,100)...(45,5)` 反向指标） |
| `score_value` 反向插值支持 | ✅ 早就有（首项得分 > 末项得分 → 自动反向） |
| **前端醒目的提示** | ❌ **完全没有** —— 只是明细表里一个普通数字 |

**排查中的一个弯路**：我一度以为「stability 维度是空的」是因为没加锚点，
其实是我**读错了 JSON** —— 保存的结果 JSON 里**根本没有 `score` 字段**
（score 是**读取时**由 `app.py` 的 `_bench_score_of` 现算的）。
直接 `BS.score(raw)` 传错了参数（第一个参数是完整 result dict，不是 raw 子字典）。
→ **以后查「某指标为什么没显示」，要先确认它是保存时算的还是读取时算的。**

### 做的三件事

**1. 采集改成「窗口采样」（实质改进）**

原来采的是**开机累计占比** `steal_total / total_total`：
- 机器开 30 天、今天才开始被超售 → 累计占比几乎不动 → **看起来一直健康**
- 分母随开机时长无限增长 → 稀释效应

改成**两次采样算窗口内占比**：
- 第一次：脚本开头（记 `STEAL1` / `TOTAL1`）
- 第二次：**脚本末尾**（磁盘 dd + 网络测试全程之后，窗口 10~20 秒）
- 公式：`(s2-s1)*100/(t2-t1)`

**窗口长度很关键**：10Hz tick 下 20 秒 = 200 jiffies，3% steal = 6 个 jiffies，
精度足够；2 秒的短窗口测不出 3% 这种量级。
（所以没放在磁盘 dd 前后 —— 那只有 1~2 秒。）

**2. 前端超售警告条**

跑分结果顶部一条醒目横幅：
- `steal ≥ 3%` → 红色「宿主机在抢你的 CPU —— 这台机器被超售了」
- `steal ≥ 1%` → 橙色「有轻微抢占，长期跑满载任务时要注意」
- `steal < 1%` → 绿色「未被宿主机抢占，正常」

明细表里「CPU 抢占率」那一行 ≥1% 时整行标琥珀色 + CPU 图标。

**3. 虚拟化类型识别（重要的区分）**

steal **只在 KVM/Xen 等虚拟化环境才有意义**。物理机 / 容器恒为 0 ——
那不是「没被超售」，而是**结构上不存在抢占**。
新增采集 `VIRT_TYPE`（`systemd-detect-virt` → `/sys/hypervisor/type` → cgroup 判断），
前端在 steal=0 且非虚拟化时提示「该机器不是虚拟化环境…这个 0 是正常的」。

### 实测验证（阿里云成都）

```
STEAL1=0 TOTAL1=2518273519
STEAL2=0 TOTAL2=2518275905
窗口 steal 占比 = 0.0000%  (窗口总 jiffies=2386)
cpu 行: cpu  1006775175 1798118 175046895 1179519176 89851181 53044179 12241187 0 0 0
/sys/hypervisor/type → 不存在（非 KVM/Xen）
```

→ **窗口采样逻辑正确**（TOTAL 涨了 2386 jiffies = 12 秒 ✅），
这台机器 steal **真的是 0**（不是逻辑坏了），
而且它是**非虚拟化**环境 → 结构上不可能被超售。

**推论**：这台机器 11.3 分的波动**不是超售**，是网络抖动。分数波动确实只是间接信号。

### 顺带修的测试抖动

`test_bench_browser` 偶发 FAIL（单独跑必过，run_checks 里会挂）：
失败项是「前端收到了后端的 start 事件」，标题停在 `PROG|正在连接服务器…`。

**根因**：Chrome 的 `--virtual-time-budget` 在**有 pending 网络请求时会暂停虚拟时间**，
于是 dump 的时机与「后端 start 事件到达」形成**竞态** —— 后端 SSH 握手慢一点就错过。
但那时**连接其实已经建立了**。

**修法**：
- 断言放宽为「已进入连接/跑分阶段且无 CONN_ERROR」
- 真正的「SSE 流通」由第 2 步的「**后端真的收到请求并完成了跑分（新增了结果文件）**」兜底
  —— 那条是端到端的，比看 start 事件强得多
- 另给测试加**内建重试**（最多 2 次；两次都失败才算真问题，不能掩盖真 bug）
